title: "Submit Payment Jobs and Monitor Asynchronous Status"

---

MAVULA Workbench accepts payment work as durable jobs and delegates execution to the settlement domain. Submitting a job confirms that the work is recorded and queued - it does not mean the payment has settled. You must poll the job status resource to track progress and determine when to reconcile downstream state. Ledger Core remains the authoritative owner of financial postings; do not infer a ledger balance change from a job status alone.

## Job types

| Type | Description |
| --- | --- |
| `PAYMENT_CAPTURE` | Initiates a payment collection from a payer on a supported rail (e.g. M-Pesa, eMola, Mkesh, bank transfer) |
| `PAYMENT_DISBURSEMENT` | Sends funds out to a payee - used for withdrawals and outbound transfers |
| `PAYMENT_SETTLEMENT` | Records a provider-confirmed settlement event against a prior capture or disbursement |
| `PAYMENT_RECONCILIATION` | Triggers a bulk reconciliation sweep to align provider state with internal records |

<Note>
  **Jobs are asynchronous - do not resubmit while a job is still running.** If a job is in `QUEUED` or `PROCESSING` state, it is already in flight. Creating a duplicate job with a different `Idempotency-Key` can result in double-processing. Always poll the existing job to completion before deciding whether resubmission is appropriate.
</Note>

## Operational states

| State | Meaning | Recommended action |
| --- | --- | --- |
| `QUEUED` | Work is durably recorded and awaiting execution | Poll with bounded back-off |
| `PROCESSING` | Provider interaction or reconciliation is in progress | Continue polling |
| `COMPLETED` | Process reached its terminal successful state | Reconcile the resulting domain state in Ledger Core |
| `FAILED` | Retry policy was exhausted or the input cannot proceed | Read `last_error`; correct the input before resubmission |

<Warning>
  If you encounter a job that cannot be completed automatically - for example because provider state is ambiguous after a timeout - escalate to an authorised operator before taking any corrective action. Do not resubmit while the original job is still running.
</Warning>

## Example: disbursement job

The payload structure changes for `PAYMENT_DISBURSEMENT`. Swap `payer` and `payee` roles to reflect an outbound transfer:

```bash
curl -sS -X POST https://workbench.mavula.dev/api/jobs \
  -H "Authorization: Bearer $MAVULA_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: d3f1a2b4-9e87-4c30-8f12-7b5c0e1a3d92" \
  -H "X-Correlation-ID: 1a2b3c4d-5e6f-7890-abcd-ef1234567890" \
  -d '{
    "queue": "payments",
    "type": "PAYMENT_DISBURSEMENT",
    "max_attempts": 3,
    "payload": {
      "idempotency_key": "disbursement_20260715_007",
      "correlation_id": "1a2b3c4d-5e6f-7890-abcd-ef1234567890",
      "rail": "bank_transfer",
      "amount": {
        "currency": "MZN",
        "valueMinor": 100000
      },
      "payer": {
        "accountRef": "institution_001"
      },
      "payee": {
        "accountRef": "customer_002",
        "displayName": "Maria Sitoe"
      }
    }
  }'
```
