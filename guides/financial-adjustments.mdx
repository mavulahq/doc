---
title: "Submit and Approve Financial Adjustments"
sidebarTitle: "Financial Adjustments"
description: "Reverse or correct a posted financial effect by submitting a maker-checker adjustment request that a separate operator must approve before it is applied."
---

MAVULA never edits financial history in place. If a transaction or journal entry needs to be undone or replaced, you submit a financial adjustment request. There are two types: a `REVERSAL` fully negates the original posting, and a `CORRECTION` replaces it with a new set of ledger lines and account postings. Both types follow the same maker-checker flow — the submitting operator cannot approve their own request.

## Adjustment types

| Type | What it does | When to use |
|---|---|---|
| `REVERSAL` | Creates an equal and opposite posting that cancels the original effect | Duplicate postings, wrong account, erroneous transactions |
| `CORRECTION` | Voids the original posting and applies replacement lending or journal lines | Misclassified amounts, wrong allocation, partial errors requiring a corrected record |

<Steps>

### Submit a reversal

Call `POST https://ledger.mavula.dev/api/financial-adjustment-requests` with a maker token. Supply `target_type` (`TRANSACTION` or `JOURNAL_ENTRY`), the `target_id` of the record to reverse, `adjustment_type` set to `REVERSAL`, and a `reason`.

```bash
curl -sS -X POST https://ledger.mavula.dev/api/financial-adjustment-requests \
  -H "Authorization: Bearer $MAKER_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 7b0491f2-eb4c-42b2-b77d-acadd27c571b" \
  -H "X-Correlation-ID: 2d94d70b-77fa-4a58-af9f-d49c6849632f" \
  -d '{
    "target_type": "JOURNAL_ENTRY",
    "target_id": "journal_001",
    "adjustment_type": "REVERSAL",
    "reason": "Duplicate posting identified in reconciliation"
  }'
```

A `201 Created` response contains the full request object in `PENDING_APPROVAL` state:

```json
{
  "id": "adj_01j9z4pq3b0000000000000001",
  "target_type": "JOURNAL_ENTRY",
  "target_id": "journal_001",
  "adjustment_type": "REVERSAL",
  "reason": "Duplicate posting identified in reconciliation",
  "status": "PENDING_APPROVAL",
  "requested_by": "operator_maker_001",
  "correlation_id": "2d94d70b-77fa-4a58-af9f-d49c6849632f",
  "created_at": "2026-07-15T11:00:00Z"
}
```

### Submit a correction

For a correction, include the optional `correction` object in addition to the required fields. A correction may carry `lending` details (amount, currency, and principal/interest/fee allocation) and `journal` details (ledger lines and account postings). Both sub-objects are optional independently, but at least the fields relevant to the original posting's structure must be valid before submission.

```bash
curl -sS -X POST https://ledger.mavula.dev/api/financial-adjustment-requests \
  -H "Authorization: Bearer $MAKER_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 9e3cf7a1-2bd5-4e88-a001-fc3d84b20197" \
  -H "X-Correlation-ID: 5f1a9c2e-8b34-4d77-b123-0e7c6d8f9a01" \
  -d '{
    "target_type": "TRANSACTION",
    "target_id": "txn_00192",
    "adjustment_type": "CORRECTION",
    "reason": "Interest allocation was miscalculated — correcting principal and interest split",
    "correction": {
      "lending": {
        "amount": "5000.00",
        "currency": "MZN",
        "allocation": {
          "principal": "4750.00",
          "interest": "200.00",
          "fees": "50.00"
        }
      },
      "journal": {
        "ledger_lines": [
          { "account_code": "1010", "debit_amount": "5000.00" },
          { "account_code": "4020", "credit_amount": "5000.00" }
        ]
      }
    }
  }'
```

<Note>
  **Correction payload rules:**
  - Debit and credit totals across all `ledger_lines` must balance.
  - The `currency` in the `lending` object must match the account's currency.
  - All source references (account codes, loan IDs) must exist in the tenant before submission.
  - Never retry a correction with changed `correction` lines under the same `Idempotency-Key`. If the correction details change, generate a new idempotency key.
</Note>

### Approve or reject the request

A different operator — one with permission to approve adjustments — calls the approve or reject endpoint. The `reason` field is required on rejection and optional on approval.

```bash
# Approve
curl -sS -X POST https://ledger.mavula.dev/api/financial-adjustment-requests/REQUEST_ID/approve \
  -H "Authorization: Bearer $CHECKER_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 147598a5-10ee-49cc-b6e5-e5415bb65844" \
  -d '{"reason": "Source documents verified — duplicate confirmed"}'
```

```bash
# Reject
curl -sS -X POST https://ledger.mavula.dev/api/financial-adjustment-requests/REQUEST_ID/reject \
  -H "Authorization: Bearer $CHECKER_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 8d2af301-cc47-4f99-b7e2-1a9031f6c884" \
  -d '{"reason": "Insufficient evidence — original transaction still under investigation"}'
```

### Verify the applied adjustment

Poll `GET /api/financial-adjustment-requests/{requestId}` until the `status` field transitions to `APPLIED` or `FAILED`. On approval, the response includes identifiers for the reversal or replacement transaction and journal entry that were created.

```bash
curl -sS https://ledger.mavula.dev/api/financial-adjustment-requests/REQUEST_ID \
  -H "Authorization: Bearer $MAVULA_ACCESS_TOKEN"
```

```json
{
  "id": "adj_01j9z4pq3b0000000000000001",
  "adjustment_type": "REVERSAL",
  "status": "APPLIED",
  "decided_by": "operator_checker_001",
  "decision_reason": "Source documents verified — duplicate confirmed",
  "reversal_transaction_id": "txn_00201",
  "reversal_journal_entry_id": "je_00315",
  "decided_at": "2026-07-15T11:30:00Z",
  "applied_at": "2026-07-15T11:30:05Z"
}
```

After the request reaches `APPLIED`, reconcile the resulting statement entries on the affected accounts to confirm the expected balance change.

</Steps>

<Warning>
  If a request reaches `FAILED` status, read the `failure_reason` field before acting. Do not submit a new adjustment against the same target without first understanding why the previous one failed — submitting a second adjustment against an already-corrected record will produce an incorrect financial history.
</Warning>
